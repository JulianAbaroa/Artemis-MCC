# Artemis.DevTools.Viewer

Group `6_DevTools` - static library inside the game process - the 3D debug viewer: free camera, map, HUD and selection.

## Responsibility
In sparse mode (Q101) it sees only the decision ticks and does not raise the every-tick demand. The HUD shows the light ticks per second and their mean time next to the sweep time.
Draws the map and a HUD over the game frame from the published Tick: a free or game camera (the game one is the camera the game rendered the frame with, see Overlay below), the collidables, zones, fixtures and
labels, an overlay with telemetry only (F3), the inspector of the selected object, and picking by ray.
It also draws that View (`ViewPass`, option `View of the watched player`, on by default): the cone of sight (`k_SightHalfAngle` and
`k_SightRange` of `Views.Raycast.Type`, from the eye along the aim, none in Full mode), a line to each player it sees, markers for its
allies, the two flags (a line to the stand when away, the carrier ringed), the radar points and the sounds, all in the color of the
relation (enemy red, ally blue, none yellow). The only thing it draws from the Tick is, in grey, the players the View does not contain, to
compare by eye with what the game shows. It also defines `EngineAccess`: the
exact members of the engine and bridge Layers the development tools may use, so they import none of those Layers.

Overlay on the game frame (VW.5a, D323, D325). With the game camera the view-projection comes from `s_render_projection` of the game (`EngineAccess::m_GameCameraService`, read at the scene point on the render thread, memory read only): the view from its axes and position, x and y of the projection as the game has them (m00, m11, m20, m21), the depth from the own `Lens.Near` and `Far`. The depth of the whole Viewer is reversed (VW.6a: near maps to 1 and far to 0, `MapService` clears to 0, `GpuPipeline` tests greater or equal), which also holds for the free camera. `ToScreen` and `ScreenToRay` use only x, y and w. The wireframe sits on its own mesh because the depth-only pass is pushed away from the camera, not because the lines are pulled forward. `SceneService::Update` computes once per frame the hidden set (`GetHiddenHandles`): the unit the game hid and the objects hanging from it in the object graph (VW.9a: the object of the first true answer of the unit test, `RenderStore::GetFirstPersonUnitObjectLastFrame`, taken up the chain of parents of the object graph to the first biped of the Tick (B3: the answer may come for a weapon first; with no biped above it nothing is hidden, so a vehicle or a turret is not), which is the biped of the local player or, with Watch POV, the one of the watched player). Only in Game mode and only when the game hid its unit in the last closed frame (VW.6b.1: `RenderStore::WasFirstPersonUnitLastFrame`, true answers of the game's first person unit test for user 0, so the overlay hides what the game hides, one frame behind when the perspective changes); with the free camera the detour answers false and the body is drawn, so nothing is hidden, and in a vehicle, a turret, dead or in a menu nothing is expected to be hidden (the perspective is not 0 there; not measured yet). `SceneService` gets the `RenderStore` by constructor. Without the unit hook (`RenderStore::IsFirstPersonUnitHooked` false) nothing is hidden, there is no fallback; the telemetry line `First person hook` says whether the unit hook is installed. `MapService` gives the set to `DynamicPass::Upload` (both dynamic passes) and `AimPass::Upload` (spheres and center markers), and the health bars (`HealthLabels`, through `LabelContext::Hidden`) skip it too. The set is part of the upload gate of both passes (`HandleSetKeyOf`). Option `Aim spheres` (key `Viewer_AimSpheres`, on by default): off, `AimPass` draws nothing. `GetEye`, `GetForward`, `ToScreen` and `ScreenToRay` follow it, so labels and picking line up. A camera that is not valid (not finite, axes not orthonormal, m00 or m11 not positive) or no read leaves Game mode with no render pose: nothing is drawn and the frame has no labels (`CameraService::HasRenderPose`); the free camera then draws with its own pose.

The 3D passes always go over the frame of the game (no option; the former `Viewer_Overlay` is gone): `MapService` never clears the color, so the frame of the game stays under what the Viewer draws (its own depth is still cleared), the map collision is drawn in depth only (it hides what comes after it, no color) and, with `Overlay: collision wireframe` (key `Viewer_OverlayWireframe`, on by default), also as visible wireframe to check that it lines up with the walls (`MapPass::Draw`, its own mesh draw apart from the depth only pass). There is no map view of its own: no cleared background and no colored collision mesh.

Where the 3D passes are drawn: `MapService::RenderScene` runs the whole 3D frame (scene update, uploads and every pass) from `RenderService::OnScene`, which `Engine.Render` calls at the exit of the opaque color pass of the game (0x26E500, inside the frame of the game, D334), the only place. It returns whether it drew: false when it is suspended, the Viewer is inactive, there is no scene or map, or Game mode has no valid game camera. ImGui, labels and panels stay in `OnFrame` at Present, which draws no 3D pass. The scene update (camera, hidden set, projection, selection) therefore happens once per frame, at the scene point, and the labels and panels of Present use its camera, hidden set and projection and the scene it acquired (`SceneService::GetFrameScene`, one acquire per frame, D294), never a newer tick. A frame without that update (a menu, a pause without a draw, no hook of 0x26E500, a target the scene blocker refuses) draws NO labels (`SceneService::HasFrameUpdate` false; `EndFrame` closes the frame at Present): nothing is drawn with the last valid data. The panels (telemetry, inspector) go on and read the last scene. An inactive Viewer draws nothing: `Layer` gives `RenderStore::SetSceneDrawRequested(IsActive())` at each Present, so the scene point returns before it measures anything (`SceneStatus::NotRequested`), and the deactivation reset (`SceneService::Deactivate`: game camera override, flying state, scene, poses, observed player) runs at Present while inactive, with or without a scene draw. When the Viewer activates and the hook of 0x26E500 is not installed, one `ERROR` line is logged. A throwing pass leaves the GPU timing closed (`GpuTimingScope`). The telemetry line `draw:` says `scene` or `none (reason)` (`RenderStore::GetDrawPlace`, `GetSceneStatus`; `none (no hook of the opaque color pass)` without the hook), plus `scene failures n` when the scene point threw.

Option `Hide game HUD` (key `Viewer_HideGameHud`, off by default, group Camera; VW.6.x): `Layer` copies it to `RenderStore::SetGameHudHidden` at the start of every Present frame, and the HUD detours of `Engine.Render` then skip the game's HUD passes (clean captures). Without the hooks installed it does nothing.

Option `Watch POV` (key `Viewer_WatchPov`, off by default, group Camera, no layer; VW.9a, D340): with the Viewer active, the option on and a player observed (`ObservedPlayerStore`, the player of the selected biped), `Layer` publishes its handle in the `PovRequestStore` of `Engine.Base` at every Present, and the game shows that player in first person in the view of user 0 (the selection follows the PLAYER, B6: `SelectionStore::Follow` keeps the player and the current biped, which `SceneService::Update` rewrites from the Tick at every frame, so the selection and the POV survive the death, the respawn and the round change of a player, and end when the player leaves the table, another object is picked or the selection is cleared. `ObservedPlayerStore` holds that player all the time. The card reads `GetSelectedPlayer` and the inspector draws only the sections of the player while it has no biped. While the watched player has no live body in the scene (`SceneService::IsPovPlayerDead`: the view shows the requested player that is not the local one, `IsPovOnOtherPlayer`, and the Tick row has no Body) `Layer` forces `RenderStore::SetGameHudHidden(true)` whatever `Hide game HUD` says, because the game repeats its loadout screen in the view of user 0 then: B7, the view and the camera are not changed, and the telemetry adds `dead, HUD hidden`) (camera, HUD, arms and weapon; see `Engine.Base`). Without those three it clears the request (the view goes back to the local player in the next frame of the game), and `SceneService::Deactivate` clears it too. It works with the Game and the Free cameras (the Free camera moves the camera and the HUD is the one of the watched player: not verified). `EngineAccess` carries the request and the status stores. The camera telemetry shows `POV hook: installed / not found` and `POV: off` or `POV: <gamertag> req 0x.. engine 0x.. local 0x.. calls n reasserts n faults n`. Only the `Layer` writes the request, from the render thread.
Option `Hide first person` (key `Viewer_HideFirstPerson`, off by default, group Camera; D331): `Layer` copies it to `RenderStore::SetFirstPersonHidden` at the start of every Present frame, and the first person detour of `Engine.Render` skips the game's arms and weapon. With the free camera they are always hidden and the game draws the player's body (the unit test answers false for user 0), whatever the option says. The camera telemetry shows `First person hook: installed (model, unit, depth pass, opaque pass)`, `third person: yes / no` and `fp unit: yes / no` (`WasFirstPersonUnitLastFrame`). `VW.6b` (hide our own biped) follows the game, see the overlay paragraph: with the free camera the overlay's own biped matches the one of the game. Without the hooks installed it does nothing.

First person mask (VW.6.y.2 B, E, D332, always on, no option): the game's first person arms and weapon are drawn over the overlay. `Layer` asks `RenderStore::SetFirstPersonMaskRequested` at the start of every Present frame while the Viewer is active (`SceneService::IsActive`; inactive, no copies), and `Engine.Render` copies the depth around the first person passes of the game (0xB and 0) and puts the copies in `FrameContext::Mask`. `MapService::Draw` gives that mask to `GpuPipeline::UpdateMask` and calls `ClearMask` after the passes, so every 3D pass skips the pixels the game writes in those passes. With `Hide first person` or the free camera the game does not draw the arms and the mask is empty by itself. Without the hook the overlay draws as before. The camera telemetry has one line `FP mask: off` (not requested), `on` or `on, no copy` (neither pair was copied in the last closed frame).

Inspector (VW.4b, D338). `InspectorService` (`DevTools.Viewer.Inspector.System`, public, built by `Layer` as `m_InspectorService`) draws the inspector of the selected object inside the Viewer tab of the Workbench: no window of its own, no pages, it is drawn by whoever calls `Draw` on the thread that draws ImGui (Present, the same one as `HudService::Draw`). Without a selection it shows `Nothing selected`, without a tick `No data`. Otherwise it takes the scene of the frame once (`SceneService::GetFrameScene`) and shows a summary always visible (the gamertag of a player biped, else the tag or the function of the entity, the handle in hex, team, vitality, and shield of a player with a body) and the sections that apply, each a collapsing header whose id is its name (so the folded state survives a change of selection), the first one that applies open by default: `View` (the selected object is the biped of a player with a View: the View of that player), `Player`, `Body`, `Loadout` and `Action` (VW.4b b2, below), `Interaction` (the object has an affordance, or it is the biped of the local player 0), `Vitality` (it has a vitality detail: maxima, damage sections and their values), `Entity` (function, binding, physics, team, vitality, capabilities), `Fixture` (teleporter, lift, barrier, zone, prop, spawn point or objective item), `Collision` (it is a collidable: transform, world mesh, bounds) and `Raw`, folded at the end (region states and raw block of the collidable, and the engine interaction state of the local player). What a section copies or computes is done only inside its header. The sections of the player (VW.4b b2) come from the `Perception.Players.Type::Player` of the biped (`Tick.Players`, found with `ObservedPlayerOf`): `Player` is the connection, local index, respawn ticks, powerup and its ticks, the score (`Tick.Match.Scores` by player handle, `none` when absent) and a two column table with every field of `PlayerTraits` (not reflectable, so no `InspectorGuiService`); `Body` and `Loadout` appear only with a live `Player.Body` and show its fields (zoom, last damager as a player name when it resolves, ticks since damage, ground and ground object, grounded, airborne ticks, crouch, velocity and speed, and the weapons with the one in the hands marked, ability and energy, grenades and selected type, objective); `Action` is the action the simulation used for the player in the latest tick, read from `PlayerActionStore::CopyLatest` by table index (`handle & k_HandleIndexMask`): buttons (hex and set bits), aim (yaw and pitch), throttle, and who wrote it: `Python / override` when `CopyOverrides` has an override for that index, `bot` when `BotStore::CopyBots` lists the index, else `engine`. `InspectorService` receives only those two stores by const reference from `EngineAccess` (`m_PlayerActionStore`, `m_BotStore`), calls nothing that writes, and the copies are made only while the `Action` header is open. Each section is a class of static functions in `Inspector/System/Section/` (`ViewSection`, `PlayerSection`, `BodySection`, `LoadoutSection`, `ActionSection`, `InteractionSection`, `VitalitySection`, `EntitySection`, `FixtureSection`, `CollisionSection`, `RawSection`). The overlay of F3 (`HudService`) shows only the telemetry: `OverlayStore` keeps only the visibility, and the arrow keys do nothing.

Agent card (VW.4c, D338, D339, Debug version: text, numbers and plain bars, no icons). `AgentCardService` (`DevTools.Viewer.Hud.System:AgentCard`, built by `Layer` as `m_AgentCardService`) draws a fixed 2D card at the bottom left of the game frame with the state of the selected player. It is drawn at Present, in `OnFrame`, right after `LabelService::Draw` and with the same gate: the Viewer active and `SceneService::HasFrameUpdate` (a frame without a scene update, a menu or a pause without a draw has no card, never data of another frame). It takes the scene of the frame once (`SceneService::GetFrameScene`) and the player of the selection with `Views.View.System::ObservedPlayerOf`: with no selection, or a selection that is not the biped of a player, nothing is drawn (it never falls back to the local player). All data come from the `Perception.Players.Type::Player` of the Tick of that scene (and the `Entity` of its biped for the vitality), nothing is read from the game memory. It is one ImGui window with no decoration and no input (`NoInputs`, `NoNav`, `NoFocusOnAppearing`, `AlwaysAutoResize`, `NoSavedSettings`), with the background opacity and the text scale of the labels (`LabelBackgroundAlpha`, `LabelTextScale`). Layer `Card` (key `Viewer_LayerCard`, label `Agent card`, default Minimal) has no flags of its own: the card asks `OptionsStore::GetLevel(Layer::Card)`. Off draws nothing. Minimal: the gamertag in the color of its team (`ColorOfTeam`) with `(bot)` when `BotStore::CopyBots` lists its table index, health and shield bars with their value, and the weapon in the hands (the tag name, no ammunition because the Tick does not carry it); a player without a live body shows only the name and `dead, respawn in N.N s` (`RespawnTicks` over `k_TicksPerSecond`). Full adds, each row only when it has a value: the primary or secondary weapon that is not in the hands, grenades by type with the selected one between brackets, the armor ability with its energy bar and `(active)`, the powerup with its seconds left, `FLAG` (with the team of the item when the entity has one) when `Loadout.Objective` is set, and the zoom. Names come from `ObjectName` and `PlayerFormater`.

Layers and levels (VW.4a, D337, D338). The options of what the Viewer shows are not loose switches: each flag belongs to a `Layer` (`View`, `Players`, `Objects`, `Fixtures`, `World`, `Health`, `Card`; `Card` has no flags) and is on according to the `Level` of its layer (`Off`, `Minimal`, `Full`). `FlagInfo` carries the `Owner` layer, the `MinLevel` and `IsInverted`, and `IsFlagOn(info, level)` (pure, in `Options.Type`) is the rule: on when the level is at least `MinLevel`, except the two inverted flags (`ObjectSelectedOnly`, `HealthSelectedOnly`) which are on only at `Minimal`, so `Full` shows every object. `MinLevel` is `Minimal` when the flag was on by default before the layers and `Full` when it was off, so every layer at `Minimal` reproduces the old defaults (a `static_assert` in `Options.Type` checks it, `FlagInfo::Default` is kept for that). The consumers do not change: they ask `OptionsStore::IsEnabled(Flag)`, which derives a flag of a layer from `GetLevel(layer)`. `SetLevel` writes a level. `SetEnabled` and `ToggleEnabled` act only on the flags that belong to no layer (`Labels`, `HideGameHud`, `HideFirstPerson`) and do nothing on the flag of a layer. Saved keys: `Viewer_LayerView`, `Viewer_LayerPlayers`, `Viewer_LayerObjects`, `Viewer_LayerFixtures`, `Viewer_LayerWorld`, `Viewer_LayerHealth`, `Viewer_LayerCard` (0 Off, 1 Minimal, 2 Full, a value out of range loads as the default), the three flags without a layer by their old keys and every scalar by its old key. The keys the flags of a layer were saved with before (`Viewer_PlayerGamertag`, `Viewer_ObjectSelectedOnly`...) are ignored on load, as the removed options of D336 are. The scalars of a layer (`ObjectArrowLength`, `HealthBarWidth`, `FixtureArrowLength`, `ShieldOpacity`, `LimitOpacity`) keep their keys and show folded under their layer. `Group` is the section of the Viewer tab of an option (Camera, Layers, Development).

Scene color scale (key `Viewer_SceneColorScale`, group Development; VW.6.z.2, D335): the overlay colors go through the exposure and tone mapping of the game, so the group Development has the logarithmic slider from 2^-12 to 2^4, default 2^-5 = the scale of the HDR target of the game, which shows the value and its log2 and goes back to the default with a double click; its `ScalarInfo::IsLogarithmic` makes the preferences write it with 6 significant digits, not `%.3f`. The scale the overlay passes multiply their RGB by at the scene point is the slider alone; `Layer` copies it to `RenderStore::SetSceneColorSlider` every Present frame, and the scale is never used outside the scene. The Viewer telemetry has one line `scene color scale x`.

Free camera (the mode Free; VW.5b, D323): it always moves the camera of the game, there is no option for it. Every frame `CameraService` asks `GameCameraService::SetOverride` for the eye, forward and up of the free camera, and the observer hook of `Engine.Base` makes the game build its camera there (position, location for culling and vertical field of view the normal way, one frame later). In Game mode, or when the Viewer is deactivated, it calls `ClearOverride` and the camera goes back to the player. There is no follow or orbit: the free camera only flies (keys, mouse, `Fov` and zoom of the free camera; the old `Follow selection`, the key left of the 1 and the `Drive game camera` and `Game camera field of view` options are gone). The overlay uses the camera the game drew this frame, exactly as in Game mode (VW.5b.1): the render pose (`GetEye`, `GetForward`, `GetRight`, `GetUp`, so the view-projection, `ToScreen`, `ScreenToRay`, `GetCenterRay` and the labels) is the position and axes of the game camera read, and x and y of the projection are the game's. The game draws one frame behind the request, so rendering with the free pose would make the game's objects slide out of the overlay while the camera moves. The free pose (`m_Eye`, yaw and pitch, `GetYaw` and `GetPitch`) is the requested pose: it feeds only `SetOverride` and the flight, and is never reseated on the game camera. Without a valid game camera the render pose is the free one. The telemetry shows `Override: on/off` and `Override faults` (only when the hook caught any fault touching the engine memory).

The overlay window (telemetry mode) shows the game camera: valid or not, position, horizontal and vertical field of view, aspect (m11 / m00) against the back buffer, the off-center terms and the distance to the eye of the View of the local player.

Latency measurement (VW.5c, telemetry only, nothing it measures changes what is drawn): `MapService::RenderScene` reads the clock once per frame (`LatencyService::ReadClock`, before the scene is chosen, VW.5d) and calls `LatencyService::Record` with it right after the scene update, at the scene point. `LatencyService` reads the clock of the engine through `EngineAccess::m_FrameClockReader` (`FrameClockReader::Read`, passing the thread context published in `CaptureStore`: TLS of the drawing thread when it has the engine context, else the published one) and pairs it with the tick of the scene that is drawn (`Match.GameTick` of the `Tick` of the `CollidableScene`, the same engine tick as `*(time globals) + 0xC`). `LatencyStore` keeps the last `k_WindowFrames` (600) frames behind one short mutex. The panel adds `Frame clock` (TLS yes or no, tick T, raw fraction f, whether the game interpolates, scene tick S and lag L = T - S), `Scene lag` (histogram of L over the window: 0, 1, 2, 3, 4 or more, negative, largest), `Camera moved within a tick` (n / m: of the m frames whose T equals the previous frame's, in n the game camera moved more than 1e-4 wu: if n > 0 while the player moves, the camera is interpolated) and `Interp probe` (Game mode only: with the eyes of the local player of two consecutive scenes, E(S - 1) and E(S) further apart than 0.05 wu, p50 / p99 of the distance from the game camera to E(S), to E(S - 1) and to the lerp of both with the fraction clamped to 0..1, over the frames whose scene is up to date (S == T), and how many frames had the scene behind (S < T)). `Observe` and `Summarize` of `LatencyService` are pure.

Scene of the game frame (VW.5d, D329). Measured in VW.5c at 60 fps (1 tick per frame, no effective interpolation): the frame of the game shows the state of the tick T - 1, with T the engine tick read at draw time. `MapService::AcquireFrameScene` therefore picks, once per frame and before the scene update, the `CollidableScene` whose `Match.GameTick` is T - 1, and the whole frame (camera, hidden set, passes, labels, panels, selection, the latency lines) comes from it. `CollidableStore` keeps the last `k_SceneHistory` (4) scenes (`Common.State.Type::SnapshotHistory`, keyed by `SceneTickOf`): `PickFor(target)` gives the exact one, else the nearest older, else the newest; `FindKey` an exact one. Without a valid clock or without a Match the newest is taken, as before. When the newest scene is older than T - 1, the thread that draws waits (always, no option) at most `k_FrameSceneWaitLimit` (2 ms, `Map.Type`) on the store (`WaitForKey`, a condition variable that `Publish` notifies; the store mutex is released while it waits and `Publish` only holds it to move pointers, but `MapService` keeps its own mutex during the wait, bounded by the 2 ms: it blocks `Suspend`, `Resume` and `Release` on the game thread only, never the AI thread). It does not wait if the tick did not advance since the previous frame (pause), if the pipeline is stopping (`LifecycleStore::CanPublish`), if the history does not arrive one tick at a time (sparse mode, Q101: the scenes come only on decision ticks). A scene that never comes is not waited for again within that frame: the nearest older is drawn. Above 60 fps the game interpolates between ticks: not implemented here (the interpolation below is the one of 60 fps, with the fraction of the clock).

Pose of render (VW.5e, D330). Measured in VW.5d: the camera of the game is the state of T - 1 moved on by the tick fraction f of the clock (`k = 0.04 + 1.04 f`, correlation 0.85), because the game draws interpolated between T - 1 and T. With the clock valid, the interpolation of the game `On` and the scene of T - 1 drawn (pick `Exact`), `MapService::UpdateFramePoses` calls `InterpolationService::Build` (`DevTools.Viewer.Interpolation.System`, the one place where it is done) with the scene shown, the scene of T if it is already in the history (it is never waited for, the 2 ms of D329 stay for T - 1) and the one of T - 2. Each dynamic collidable (matched by full handle, so index and salt) is placed by `Common.Math.System::ResolveRenderPose` between its pose in T - 1 and in T by f (`Exact`: position in a line, forward and up blended and made unit and orthogonal again), or, without T, on from T - 2 at constant velocity: pose(T - 1) + f * (pose(T - 1) - pose(T - 2)) (`Extrapolated`). Not blended (drawn as the scene shows it): an object missing in the scene used, a step past `k_InterpolationSnapDistance` (2 wu per tick: teleport, respawn, change of seat), Fixed and Phased objects (`Entity.Physics`) and objects that did not move. The result is `FramePoses`: per object the `Offset` (render position minus the position in the scene shown) and a rigid 3x4 `Transform`, with a `Revision` that changes with f and the tick so the passes that cache their upload know the poses changed. It is kept by `MapService` and copied to `SceneService` (`SetFramePoses`) for the labels. With the interpolation of the game `Off`, no clock or a pick that is not `Exact`, the poses are empty and nothing changes from VW.5d. Uses: `DynamicPass` moves every part of an object by the `Transform` of its object when it fills the instances (CPU work per instance only, the vertices of the geometry are not touched, and the instances are rebuilt and uploaded every frame while the poses are active, as the Revision breaks the cache gate); `AimPass` moves the spheres of an object by its `Offset`; `PlayerLabels`, `ObjectLabels`, `VehicleLabels` and `HealthLabels` move their anchor by the `Offset` of their object handle (`ShiftedBy`); `ViewPass` starts the cone, the lines to the players it sees and the sound arrows from the eye of the watched player moved by the `Offset` of its biped, and `RaycastPass` starts every ray from its origin moved by it (the end stays where the scene hit); the `Interp` telemetry. Not moved: what the View of the watched player sees (other players, flags, radar markers, hidden grey markers), the distance rows of the labels, the fixture, zone, limit and interaction labels and passes, the panels (they show the values of the scene), the selection (ray against the boxes of T - 1) . Skeletal bones are moved with the rigid move of the object, not interpolated one by one. The telemetry line `Interp (600 f): exact a  extrap b  none c` counts the frames drawn for a target tick by how the poses were found (`exact` T in the history, `extrap` only T - 2, `none` the pose of the scene as is).

## Does not
- Take part in the tick: it reads published values only, after the tick (the observers of the AI thread).
- Build the collidable scene inside the pipeline: its `CollidableSceneService` asks `Perception.Collidable.System` for it on the AI
  thread after the tick, and only while the viewer camera is active (free or game).

## Input and output
- Input: the Tick (taken with the collidable scene, published together after the tick, D294), the stores of the pure projects, `EngineAccess`, the window input of `Engine.Render`.
- Output: drawing on the game frame; the viewer options in the preferences file.

## Public interface
Other projects may import only these modules; everything else in the project is internal.

| Module | What it gives |
|---|---|
| `DevTools.Viewer.Layer` | The facade: camera, selection, overlay, options and the services that draw. `SceneService` writes in the `ObservedPlayerStore` of `Services` the player of the selected object when it is the biped of a player (`Views.View.System::ObservedPlayerOf`, pure), else none (the local player), so the AI thread gives that player a View (F4.2) and selecting a bot shows its View without moving the camera. The camera, the labels, the aim hit label and the rays and the View it draws come from the View of the watched player (`SceneService::GetObservedView`: the observed one, else the primary local player), and the free camera starts on the View of the local player. |
| `DevTools.Viewer.Access.Type` | `EngineAccess`: what the tools use of the engine and the bridge (it also carries the `FrameClockReader` of the latency measurement, the `OracleStore` of the raycast oracle and the `MapVariantDecodeStore` the bench asks decodes through), built by `Mod`. |
| `DevTools.Viewer.Camera.Type`, `DevTools.Viewer.Camera.State` | Camera modes (Free and Game), lens, rays and the camera input. |
| `DevTools.Viewer.Options.Type`, `DevTools.Viewer.Options.State` | Viewer options, the layers with their levels (`Layer`, `Level`, `IsFlagOn`, `OptionsStore::GetLevel` and `SetLevel`) and their preference keys (`Viewer_Layer<Name>` the level of each layer, `Viewer_HideGameHud` the one of the game HUD, `Viewer_HideFirstPerson` the one of the first person arms, `Viewer_PlayerView` is the one of the View pass, `Viewer_AimSpheres` the one of the aim spheres, `Viewer_OverlayWireframe` the one of the collision wireframe, `Viewer_SceneColorScale` the one of the scene color scale). |
| `DevTools.Viewer.Interpolation.Type`, `DevTools.Viewer.Interpolation.System` | The poses the overlay draws the objects with between two ticks (VW.5e): `FramePoses`, `ObjectDelta`, `k_InterpolationSnapDistance` and `InterpolationService::Build`. |
| `DevTools.Viewer.Latency.Type`, `DevTools.Viewer.Latency.State`, `DevTools.Viewer.Latency.System` | The latency measurement of the overlay: window of frames, `LatencyService` (`Record`, pure `Observe` and `Summarize`) and the report the panel shows. |
| `DevTools.Viewer.Inspector.System` | `InspectorService`: the inspector of the selected object (summary and sections, see Inspector above), drawn inside the Viewer tab. |
| `DevTools.Viewer.Overlay.State`, `DevTools.Viewer.Selection.State` | Visibility of the telemetry overlay (F3); selected object and pick requests. |

## Depends on
Every pure project, `Services`, `Bridge.Transport`, the five `Engine.*` projects and `DevTools.Gui`; it imports engine modules only

## State between ticks
Camera, selection and options (saved in the preferences file; the keys never change).

## Threads
Render thread for drawing, for reading the game camera and for writing the camera override (the one writer of the `CameraOverrideStore`); window thread for input; AI thread only for the collidable scene, after the tick. The camera and option stores are atomic. `CollidableStore` readers take a short mutex (history of scenes, never held while waiting or while a dropped scene is released). `MapService::AcquireFrameScene` runs on that thread too and may wait up to 2 ms there (the game render thread at the scene point, or Present), see the scene of the game frame above. `LatencyService::Record` runs on the thread that draws the overlay (the game render thread at the scene point, or Present), the panel reads at Present: `LatencyStore` shares them with one short mutex, and the clock is read without waiting for the game thread.

## Errors
A failure in the viewer never reaches the tick; the viewer just draws nothing.

## Requirements
Never blocks the AI thread. Collidables are computed only while the viewer camera is active, outside the tick.

## Tests
`CollidableSceneTests` (the pipeline builds no scene; the scene on demand) and `SnapshotHistoryTests` (the pick of a scene by tick, the history and the wait, in `Common.State.Type`) in `Artemis.Tests`; the rest is manual.
