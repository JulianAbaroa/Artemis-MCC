# Artemis.DevTools.Workbench

Group `6_DevTools` - static library inside the game process - the launcher, inspectors, recorders and the in-game test bench.

## Responsibility
- The Viewer tab (VW.4a, `ViewerUIService`, `DevTools.Workbench.Viewer.System`), second after Simulation (the tabs go Simulation, Viewer, Definitions, Settings, Logs): a state line (Viewer active or not, Free or Game, the player it follows, from the observed player store and the last tick), the preset combo (Debug only, Showcase and POV disabled until VW.10), the Camera block (Viewer active, mode, zoom, Hide game HUD, Hide first person, Watch POV, Agent strip, Roster: agents only, custom speed and the two fields of view) with its Director section (VW.14, VW.16: Play / Stop with the sequence that plays and the progress of the shot, the map key and the file of its shots with the message of the last load or save (a file of the first version says it was migrated), the `Auto-play on match start` checkbox and the orbit speed slider, `Add fixed (free camera)`, `Add orbit (around center)` and `Add POV` (they add to the library and, with an active sequence, to its end), the SEQUENCES block (a combo with the active sequence, `(none: the whole library)` included, a name field with New / Rename / Delete, and the list of its shots, each with its kind and name, the shot that plays marked, reordered by DRAGGING with ImGui drag and drop, with `x` to take one out of the sequence without deleting it) and the LIBRARY table (a drag handle that reorders the library, an On checkbox, an editable name, the kind, the end as a combo `Seconds` / `Rounds` / `Hold` with its value, the turn speed of an orbit, `+` to append the shot to the active sequence and `Del`; dragging a row of the library onto the list of a sequence inserts the shot where it is dropped); it only edits the `DirectorStore` of the Viewer through `DirectorStore::Edit` with the pure functions of `DevTools.Viewer.Director.System`), the Layers block (the Labels switch with its four scalars folded, then one row per layer (the last one, `Agent card`, has no flags: its tooltip describes its levels) with an Off, Minimal and Full selector, or a combo in a narrow window, whose tooltip lists what each level shows, built from the flag table, and the scalars of the layer folded below) the Inspector header, open by default, which draws `InspectorService` of the Viewer (the selected object: summary and sections), and the Development header, closed by default (scene color scale). Nothing of the Viewer options is in the settings tab any more.
- The launcher and its tab windows: simulation (a fixed strip with speed, pause and the state dots, then the collapsible sections MATCH, BOTS, TICK DUMP, LOCAL PLAYERS and DEVELOPMENT, whose open state is saved as the `Simulation_<Section>` preferences, usable at 480 px; the player actions window opens from DEVELOPMENT; BOTS has one roster editor, with counters for Red, Blue, Auto and the other teams, whose "Apply now" is an immediate roster-only request to `MatchSetupService` and "Next round" the normal one, a chip with the result of the last request, a table of the bots and the detail of the picked one; MATCH has a New from .mvar row (Q106): the `.mvar` files by the name inside them, read again each time the list opens, with the description, file, account and date in each tooltip, the template configuration (default Map CTF 1v1 First), the name (prefilled with Map plus the name, an invalid or existing one in red with the reason) and Create, which has the MCC thread decode the file and saves the configuration with `CreateFromMvar`, with a chip pending, created or rejected with its reason), definitions inspector,
  logs, settings and hotkeys (icons from `Resources/`, stb compiled here). The settings tab has the collapsible sections Data (local storage state, Save and Load preferences, Delete data), Interface, Hotkeys (the Viewer keys included: F4, TAB, F6, the up and down arrows for the next and previous player, F7, Insert and the right and left arrows of the director (next and previous shot of the playlist), the mouse and wheel) and Folders, usable at 480 px (rows follow the window width, buttons wrap), whose open state is saved as the `SettingsTab_<Section>` preferences. Load preferences calls `PreferencesService::Load` from the render thread: it fills the same stores the sliders write.
- The raycast oracle (R3, D272, `Oracle`): checks in game that the rays of Artemis give what the engine gives and measures what a ray costs the engine. Off by default and never saved as on (only its rays per batch, default 16, and its period in ticks, default 1, are preferences: `RaycastOracle_Rays`, `RaycastOracle_EveryTicks`). Every period it hands `Engine.Capture` a batch with the rays of the last tick (aim and perception, rebuilt from the View) and random ones from the eye of the watched player (fixed seed, 100 m), reads what the game thread traced, compares it with `Raycaster::Cast` (static, same ray) and with the rays of the View of the watched player (the one the Viewer follows, else the local player, one or two ticks apart), and every 10 s writes `[RaycastOracle] INFO:` to the log and `RaycastOracle/<date>.txt` in the storage folder: counters, the 20 worst differences and the engine cost per ray (mean, p50, p99) for the static test and the test with objects. The comparison is `Views.Oracle`. Exception to "observers must not block", only while the oracle is on: its observer writes the report file (a few KB of text, truncated and rewritten every 10 s) on the AI thread, and the rays it casts with `Raycaster` cost up to 64 casts per tick. Nothing in the repo posts work to the Dump thread (it only runs the TickDump queue), so the write stays there.
- Recorder: TickDump (`.tdump` + `.sdump` of every tick, written by the dump thread; each `.tdump` record also carries the real
  time since the previous one).
- The in-game test bench: takes scenarios from the exchange folder of `Tools/game.py`, plays their matches through the match cycle,
  checks them and writes `state.json` and the report. A match may ask for the TickDump (`tickdump` for the `.tdump`, `tickdump full`
  for the `.tdump` and the `.sdump`), which the bench starts at the first tick of the match and stops at its end.
  Every-tick demand (Q101): TickDump raises it while it records (from its start to its stop or its failure) and each bench match raises it
  for its whole duration, so the pipeline runs on every tick and the checks, the probes and the dump see every tick even if a client asked
  for sparse. A match with `every_tick off` does not raise it, so a client may run the sparse mode there (the bench then sees only the
  ticks of the decisions); it cannot go with `tickdump` or `events`. The `perf` block also has a `light` entry (ticks, mean and max in microseconds).
  Each match report also gets a `perf` block (omitted when the run had no sweeps): the cumulative telemetry counters and the Lockstep
  counters are photographed when the run begins and when it ends, and the difference gives ticks, wall, engine (without the Lockstep
  wait), read wait (with `capture_ms`, `queue_wait_ms` and the `queue_depth` avg and max, D305) and sweep times (avg, p50, p99, max) per tick or sweep, the average of each sweep stage, and the Lockstep waits, plus the highest first-unused slot (`object_slots_max`) and live count (`objects_max`) of the engine object table.
  Match key `director` (VW.16, line `director <sequence>`, JSON field `director` of `Tools/game.py`, a non-empty string): the Director of the Viewer plays that sequence of the shot library of the map (`%LOCALAPPDATA%\Artemis\Director\<map key>.txt`) from the load of the match. `ParseSequenceRequest` of `DevTools.Viewer.Director.System` reads the value (trimmed and sanitized as the names of the file are), an empty value fails the scenario when it is parsed. The path Bench to Director is direct and allowed: this project depends on `DevTools.Viewer`, so `BenchUIService::BeginMatch` writes `DirectorStore::SetLoadRequest(sequence, afterStarts)` (bench thread) right before it requests the launch, with `afterStarts` the engine start count it also keeps as `run.EngineStarts`: the request belongs to the first engine start ABOVE that count and no other start takes it. A match without the key calls `ClearLoadRequest`, and `EndMatch` (a finished match, a failed launch or load, a timeout) calls it too, so a request that no start took never plays in another match. `Layer` of the Viewer, at the first Present that sees the new engine start (`DirectorService::Observe`, which calls `TakeLoadRequest(observedStarts)`), takes it, makes the Viewer active and the director plays that sequence from its first shot in place of the active one, without writing the file of the user. A sequence that does not exist in the file is a `[DirectorService] WARNING:` in the log and the active one plays. The bench never writes anything else of the director.
  Match key `inputs` (VW.9c.3 C, line `input <all|bots|locals> <from> <to> <d> [move=f,l] [look=yaw,pitch] [level=names|-] [edge=names|-] [turn=rad]`,
  parsed by `ParseAgentInputLine` of `Control.Client.System`, after the players word): while a tick of the match is inside the range (to 0 = the end) the bench gives each selected player
  the same AgentInput as a new window of d ticks (`PlayerActionStore::SetAgentInput`), once per d ticks, at the sample after it is due (the bench samples the ticks,
  so the ticks between samples repeat the held controls and axes without a press and without look); outside every range it clears it. The last input whose range holds
  the tick wins. It is exclusive with an action mode that sets an override of the same player: a scenario with an action mode (other than the engine's own) and an input for the same players in overlapping ticks is rejected when it is parsed. The bench keeps the applied inputs and clears them by player handle. The bench never writes the control block of a local player.

## Does not
- Take part in the tick: the AI thread only hands it the immutable `ObservedTick`.
- Import the engine Layers: it uses `EngineAccess` from `DevTools.Viewer`.

## Input and output
- Input: `ObservedTick` per tick, `EngineAccess`, user actions, bench scenarios.
- Output: windows on the game frame, `.tdump`/`.sdump` files, bench reports, preferences.

## Public interface
Other projects may import only these modules; everything else in the project is internal.

| Module | What it gives |
|---|---|
| `DevTools.Workbench.Layer` | The facade: stores and services of the launcher and its tabs. |
| `DevTools.Workbench.TickDump.System` | The TickDump service the dump thread runs. |
| `DevTools.Workbench.Oracle.System` | The oracle service `Mod` runs as a tick observer (`OnTick`, AI thread: it never waits for the game thread) and draws in the Simulation tab. |
| `DevTools.Workbench.Bench.System` | The bench service the bench thread runs. A match has one setup at load (LS.2, D286): `preset <name>` or `preset none` (a name that cannot be loaded ends the match with `no-preset`), `map <config name>` or `map none` (the map variant of a recorded config, Q98, D266; a name that cannot be read ends the match with `no-map`) and the bots with `roster <8 counts> auto <n>` (D284). The three are made one request to `Engine.Base` `MatchSetupService` before the launch and applied whole or not at all at the load (the bots at the first tick); a match without a roster asks for an empty one, so the previous bots are taken away. `create_config lobby|match <file>|<template>|<name>|<config>` (Q106) is a decode that also makes the config `<name>` from `<template>` with `CreateFromMvar` (an older config of that name goes to `_deleted` first, so the scenario runs again), and with a config to compare it reports the bytes of the whole file that differ, how many are inside the map variant block and the runs outside it (`Tools/game.py`: a decode with `template` and `name`; the match may play the created config). `decode_mvar lobby|match <file>|<config>` (Q106) has the engine decode a `.mvar` once in the lobby, before the launch, or while the match runs (one at a time through `Engine.Match` `MapVariantDecodeStore`, 10 s to be answered), and adds a check `decode_mvar <file>` whose detail is the name, version, quotas, map id and placements of the decoded map variant and, if a config is given, the bytes that differ from its map variant block and their runs (a decode that fails, or a match that ends before it ran, fails the check; `Tools/game.py` writes the line from the `decodes` key of a match, a relative file from the repo). `round_setup preset=<name|none>; map=<config|none>; roster=<8 counts> auto <n>` (any of the three, in any order) is one setup per next round: asked for while the round before runs and applied at its end (the old `round_roster` key is gone; the `rosters` shortcut of `Tools/game.py` writes setups that only change the roster, and `setups` with `rosters` is an error there). A field a setup leaves out keeps the earlier value. Checks: `setup_ok` (at the start of every round in play the preset, the map variant and the bots of the Tick match the setup of that round, accumulated, and a requested setup ended AtLoad or Applied with no reason, so a partial roster fails it), `roster_ok` (the same rows, only the bots), `preset_applied [<name>]` and `map_applied [<name>]` (the load ended AtLoad and the active preset or map variant is the one asked for). Its panel in the Simulation tab has no controls (Claude runs scenarios with `Tools/game.py`): one status line (Off, Waiting, or Running with the scenario, the match and its phase), a `Last:` line with PASS or FAIL and the local time of the last finished scenario (the same criterion as the final report), and, only while a scenario runs, the Setup line (preset, map variant, roster and the state of the last request) as a chip. The Simulation tab shows the same Setup line and an editor of the counts per team that requests a setup with only the roster. |

## Depends on
Every pure project, `Services`, `Bridge.Transport`, the five `Engine.*` projects, `DevTools.Gui` and `DevTools.Viewer`.

## State between ticks
Window state and preferences, the recording queues and files, the running bench scenario.

## Threads
Render thread for the windows; the AI thread only pushes to the recorder queues (bounded); the dump thread writes the dumps; the
bench thread advances the bench five times per second.

## Errors
A tool that fails does not affect the tick; a bench match that fails or passes its limit is left and the next one starts.

## Requirements
The AI thread never waits for a tool except the queue of the dump, which is capped in bytes (256 MB of what the entries keep alive; an entry alone above the cap still goes in; no Tick is lost).

## Tests
The formats it writes are tested where they live (`TickDumpWriterTests` for `Bridge.Codec`, `SnapshotRecordTests` for
`Blam.Layout`); `Tools/Tests/test_tickdump.py` covers the reader. The windows are manual; the bench is itself the in-game test
harness.
