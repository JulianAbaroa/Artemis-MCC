# Artemis.Engine.Capture

Group `5_Engine` - static library inside the game process - copies one tick of the game into a Snapshot.

## Responsibility
The tick hooks (`ExecuteGameFrameDetour`, `SimulationTicksDetour`) that close every logic tick and hand it to the `TickProducer` port (D305)
(the owner copies the tick with `CaptureService` on the game thread and queues it for the AI thread) (`SimulationTicksDetour` also ends the round on request; it calls `Engine.Base` `MatchSetupService::UpdateBreak` right after the end of round, before the ticks of the frame (also in a pause), which applies the match setup - preset, map variant and bots - at a round break, D286, and then `PovService::Update`, which keeps the view of user 0 on the player the Viewer asks for, VW.9a, D340); the locators of the object, player and interaction tables; and `CaptureService`, which copies the live objects (the slots below the first-unused mark of the engine object table, at most its capacity and `k_MaxObjects`, and tells `Services` Telemetry the mark and live count) and every
memory region of `RegionId` into a new Snapshot and publishes it. `CaptureLight` (Q101) copies only what the flag pass needs, into a light Snapshot (`IsLight`) that it does not publish: the objects of kind `k_LightKindId` (the weapons: the flags are weapons, and this project cannot filter by tag) and the regions of `IsLightRegion` (game clock, game engine globals, megalo objects). It reads the same table with the same walk, takes no telemetry and does not check the capacities.
The tick gate (TG.1, D380): `TickGateDetour` hooks the pause predicate of the engine (FUN_1800356ac) but answers the `TickGate` port only for the call that `SimulationTicks` makes at the start of every tick (return address `SimulationTicks + 0x6B`): the other callers always get the engine answer. If the port says to hold, the engine cuts its loop as it does for its own pauses, the frame ends and the engine draws. `Install` receives the address of `SimulationTicks` from `SimulationTicksDetour::GetFunctionAddress` (its start is overwritten by that hook, so it is not scanned again) and installs only when `ExecuteGameFrameDetour` is installed too (without it a held frame would produce a tick again), checks the `E8` call at `k_SimulationTicksPauseCallOffset` and the exact prologue `k_PauseCheckPrologue` at its target, and on any failure logs one ERROR and installs nothing (the game then waits for Python inside the tick, as before).
On the path without the frame hook (`ExecuteGameFrameDetour` not installed) `SimulationTicksDetour` produces one tick per call even when the call ran several, so the others count as dropped ticks in the telemetry (RV.1).
The raycast oracle (`Oracle`, R3, D272) is a development tool that lives here only because it calls an engine function: `OracleService` runs at the end of `CloseTick`, after the copy of the tick (the producer returned), and traces the rays of the batch the dev tools left in `OracleStore` with `collision_test_vector` (found by its RVA and the start of its prologue with `AOBService::FindFunctionAtRva`). It is off by default: while off a tick costs one inline atomic read of `OracleStore::IsEnabled`, no hook is added and nothing is copied.

The region `PlayerActions` (D371) is the one region that is not game memory: `Capture` asks the `AppliedActionsPort` (`Engine.Base.Action.Type`, connected by `Mod` with `SetAppliedActionsPort` to the `PlayerActionStore` of `Engine.Control`, which this project cannot see) for the mask and the 16 actions the simulation applied in the tick. Order inside the tick (read from the code of `ExecuteGameFrameDetour` and `PlayerActionDetour`, still to confirm in game (the tick of `TimeGlobals` against the `Sequence`): the test `PlayerActionsAreTheLatestThePortGaveWhenTheCaptureRuns` only checks that the region is what the port gave): `PlayerActionDetour` publishes the actions of tick N right before the engine applies them, inside tick N (ExecuteGameFrame calls ApplyPlayerActions), and the capture closes tick N at the start of the next ExecuteGameFrame or at the end of the simulation call, before tick N + 1 publishes, so the region holds the actions of the same tick as the rest of the Snapshot. The port gives plain data (`AppliedActions`: `Sequence`, mask, the 16 raw actions, filled by `PlayerActionStore` under its mutex) and `CaptureService` does the layout of the region. Without a port, before the first published tick and in `CaptureLight` the region is empty, with no error and no log per tick. A tick without published actions (the null update at the end of a match, where the ActionTick repeats) leaves the `Sequence` as it was: the full capture keeps the last sequence it copied and leaves the region empty when it did not advance, so the region is never a stale repeat of the previous tick (`Cleanup` forgets the sequence). The interaction records inside each action (+0x54) are armed by the engine (local players) or by `BotService` (agents) from the world as it stood before the tick, so they describe the objects of the previous Snapshot, as the shadow check `InteractionLate` shows for the locals.

## Does not
- Interpret what it copies: that is `Blam.Runtime`.
- Decide which rays to trace or compare the answers: that is the oracle of `DevTools.Workbench`, which only uses `OracleStore`.
- Apply actions or end rounds by itself (`Engine.Control`, `Mod`).

## Input and output
- Input: the game memory and the layouts of `Blam.Layout`.
- Output: the published `Snapshot` in `CaptureStore`, and the ticks handed to the `TickProducer` port.

## Public interface
Other projects may import only these modules; everything else in the project is internal.

| Module | What it gives |
|---|---|
| `Engine.Capture.Layer` | The facade: `CaptureStore`, `CaptureService`, the three locators, the two tick detours and `TickGateDetour`. Owner only. |
| `Engine.Capture.Type` | The tick queue constants (`k_TickQueueDepth`, `k_ReadTimeout`), `ProducedTick` and the `TickProducer` port the owner implements (D305), and the `TickGate` port (`IsTickHeld`, before every tick, may wait `k_LockstepHoldBudget`) that `TickGateDetour` asks (TG.1, D380). |
| `Engine.Capture.System` | `CaptureService` (`Capture`, `CaptureLight`), for the owner that implements `TickProducer`. |
| `Engine.Capture.State` | `CaptureStore`: the addresses the capture copies from and the last published Snapshot (for the dev tools). |
| `Engine.Capture.Oracle.Type`, `Engine.Capture.Oracle.State` | The raycast oracle hand-over (R3, D272): `OracleBatch` (rays the dev tools ask for), `OracleOutcome` (what the engine answered and how long each call took) and `OracleStore` (the on/off flag, the status and the lock-protected hand-over between the AI thread and the game thread). |

## Depends on
`Common`, `Services`, `Engine.Base`, `Blam.Layout`.

## State between ticks
The table bases and the engine thread context found by the locators; the last published Snapshot. `CaptureService` also keeps a pool of up to `k_TickQueueDepth` + 4 = 8 Snapshots it reuses (D276, D305: the queue, the one the AI thread processes, the one being filled, the published one and one an observer keeps): `Capture` fills one that only the pool holds (never the published one, nor one the queue, the AI thread, a reader, the dump queue or a viewer still holds), emptying its objects and reusing the capacity of its arena and regions. A Snapshot nobody can release because it is held is simply not reused, and above the pool capacity a new one is made and not kept. A new teardown epoch starts a new pool. `CaptureLight` takes its Snapshot from the same pool and empties the regions that are not light, so a reused Snapshot never carries a full capture's regions.

## Threads
The tick hooks run on the game thread and, between two ticks, call `TickProducer::Produce` (D305): `Capture` and `CaptureLight` run there, on the game thread, while the engine writes nothing, and the result goes into the queue of the AI thread. The game thread waits only if the queue is full (`k_TickQueueDepth` = 4, one decision cycle), at most `k_ReadTimeout` (100 ms): then the tick is not queued and counts as lost. The AI thread never reads game memory.
`TickGate::IsTickHeld` runs on the game thread before each tick and may wait up to `k_LockstepHoldBudget`.
The oracle runs on the game thread between two ticks (`CloseTick`), right after the copy of the tick (the producer runs first, so the capture is complete) and when the engine runs nothing else: `collision_test_vector` reads the game state and writes only the scratch of the thread context of its caller, which is the game thread's own block of the 6 of the pool (A20 sec. 2). `OracleStore` is the only thing the AI thread and the game thread share there, and the game thread only tries its lock.
The pool is filled only by `Capture`/`CaptureLight`, on the game thread (it needs no lock): the AI thread releases a Snapshot just by dropping its reference, and `AcquireSnapshot` takes it again when only the pool holds it (an acquire fence orders the AI thread's reads before the game thread writes it again). `Cleanup` (game thread) only drops the published Snapshot of `CaptureStore`, and a new epoch replaces the pool on the next capture.

## Errors
Once per map load (per teardown epoch of `LifecycleStore`), `Capture` compares the capacity of the engine object and player tables (header of the data array) with `k_MaxObjects` and `k_MaxPlayers`: a difference is a WARNING with both values (a larger engine table is walked only up to `k_MaxObjects`). `collision_test_vector` is used only if the unwind table of the module says a function begins exactly at its RVA and the bytes there are its whole prologue (the pushes and the exact frame of 0x16910 bytes, no slack). Rays that are not finite or longer than `k_MaxVectorLength` are skipped on the game thread (counted, not traced), and the engine gets a result buffer bigger than the 0x70 bytes with a canary past them. If the function is not found, raises an access violation (the only exception handled, its code is logged) or writes past its result, the oracle logs an ERROR saying the state of the game is untrusted, goes to `Unavailable` and does nothing more until the game restarts: a fault inside the engine may have left its state half written, so restart the game before trusting a run. A region that cannot be read is left empty in the Snapshot and its flag stays off; before the thread context or the object table
is found, the Snapshot says so and nothing is copied.

## Requirements
The copy of a tick stays short: the game thread pays it on every tick (telemetry: read wait = capture + wait for room in the queue, with `capture_ms` and `queue_wait_ms` apart). The oracle never runs inside it and costs the game thread nothing while it is off.

## Tests
`ReplayTests.Recordings` uses Snapshots this project recorded; `OracleStoreTests` (the hand-over without MCC), `CaptureServiceTests` (the capacity check over fake memory, and `CaptureLight` equal to `MakeLight` of the full capture, not published, sharing the pool; the region `PlayerActions` from a hand made `PlayerActionStore`, empty without a port and in the light capture, and the tick order); the capture itself is checked in game (golden film and the bench).
