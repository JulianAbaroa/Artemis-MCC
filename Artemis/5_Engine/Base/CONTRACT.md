# Artemis.Engine.Base

Group `5_Engine` - static library inside the game process - the base every other engine project builds on.

## Responsibility
Talking to the game process at the lowest level: detours and patches (MinHook, compiled here), signature (AOB) search, safe memory
reads, the engine's thread-local context, and the lifecycle of the game (engine initialized, map file opened with its path,
subsystems destroyed, the tick in progress of the AI thread and the load of its resources). Also the host side of MCC: the game manager vtable and the local users
Artemis adds next to the real one (split-screen). And the gametype presets (Q97, D264): the compiled files of `Tools/presets.py` are read
from `<storage>/Presets`, the active one is kept in a store and `PresetService` writes it into a copy of the start configuration. The map variant (Q98, D266) and the bots (D284) go the same way. The three are one
match setup (LS.2, D286): `MatchSetupService` takes one request (`preset?`, `map?`, `roster?`) and applies it whole or not at all, at the start of the
match or at a round break, always in the order preset, map variant, roster. `PresetService` and `MapVariantService` only read, plan and write
buffers they are given; they keep no request and no result.

## Does not
- Capture the tick (`Engine.Capture`), apply actions (`Engine.Control`), launch matches (`Engine.Match`) or draw (`Engine.Render`).
- Install anything or register callbacks by itself: `Mod` connects the lifecycle and installs the hooks.

## Input and output
- Input: the game process.
- Output: lifecycle events and status (`LifecycleStore`), hook and memory services for the other `Engine.*` projects, the local
  users and the game manager functions.

## Public interface
Other projects may import only these modules; everything else in the project is internal.

## Depends on
`Common`, `Services`, `Blam.Layout` (the pure logic of the presets and the offsets of the game engine globals).

## State between ticks
The engine status, the windows of the tick and the load in progress, the addresses found by signature, the local users and their profiles, the active preset with the base values, the active map variant, the active bots and the request waiting with the result of the last one (they stay between matches; `Cleanup` of the match neutralizes the result).

## Threads
- First person signatures (D331): `k_FirstPersonModel*`, `k_FirstPersonDepthPass*` (0x26DA08, `void(void* view, int32 pass)`, the pass between entry and exit of the first person draw, whose call with pass 0xB writes the depth of the arms and weapon: VW.6.y.2 A5, B; the signature of 0x26E2A0 of A4 was removed because it does not write the depth), `k_FirstPersonForward*` (0x26EA78, `void(void* view, uint8 phase)`, the forward pass of the view, hooked and called untouched), `k_OpaqueColorPass*` (0x26E500, `void(void* view)`, the opaque color pass of the view, once per view, called after 0x26EA78 phase 0: the overlay draws at its exit, VW.6.z.1, D334) and `k_IsFirstPersonUnit*` in `Engine.Base.Memory.Type` (RVA, exact prologue, window 0) are used by `Engine.Render` to hook the arms pass, the depth pass, the forward pass, the opaque color pass and the first person test. `CameraOverrideStore::Read(k_OverrideMaxAge)` is the one rule for "Drive is active": the observer camera hook and the first person hooks use it, wait free and without allocations from any thread.
- Camera override (VW.5b): `CameraOverrideStore` is double buffered, written by the Viewer on the render thread (one writer, checked in debug builds) and read by `ObserverCameraDetour` on the game thread without waiting. The detour allocates nothing, logs nothing and blocks on nothing, validates the pose again before it writes game memory and guards every access to the engine with `__try`, counting the faults in the store. Its in flight scope covers the call of the original, so `Uninstall` (at `OnUnhook`) waits for the threads inside the trampoline.
- Engine functions and anything that needs the engine's thread context run only on the game thread.
- Engine clock (VW.5c): `FrameClockReader::Read` is called from one thread, the render thread of the Viewer. It reads memory only (guarded reads), takes no lock and never waits for the game thread. The context of the game thread is read from another thread through the pointer it published, so a value can be a tick old.
- Memory reads run on the game thread, between two ticks (D305): `Engine.Capture` copies each tick there and queues it, so the AI thread never reads game memory.
- `LifecycleStore` is thread-safe: hooks and the main thread write it; the AI, input and main threads wait on it. At teardown the game thread waits up to 1 s for the load of the Artemis resources and up to 1 s for the tick the AI thread is processing (C.9, D297, D305): it reads `CanPublish` before it publishes and between pipeline stages, so it stops at the next stage boundary and is discarded, and the Cleanup runs with no stage running. The ticks still in the queue are not waited for: the AI thread discards them (counted as discarded) once it sees the new epoch, and a tick it takes from the queue after the teardown began finds the epoch changed (`BeginTick` goes up before it checks, and `WaitForTickEnd` puts a full fence before it looks, so one of the two sees the other). `MarkLoaded` publishes the epoch the AI thread loaded the map resources for, and the game thread queues ticks only while it equals `GetTeardownEpoch`: after a teardown it never matches until the next load, so no tick of the old map is queued and none of the new one before its resources exist. Only an AI thread that hangs past 1 s lets the Cleanup run anyway (it is never held longer by the AI thread). `GetTeardownEpoch` goes up with every `TearingDown`, so a thread that slept through the teardown, or a tick that only saw `Destroyed`, still finds its per-map state stale and resets it. The teardowns with timeout and the discarded ticks are counted (game thread and AI thread, atomics) and shown in the teardown INFO.
- Remaining risk: a stage running longer than 1 s (a hung AI thread) can still overlap the Cleanup; the teardown then logs the timeout. Moving the cleanup of the stores to the AI thread was discarded (D297): the next map opens its file on the game thread before the AI thread would clean.
- `MapVariantStore`, `PresetStore` and `MatchSetupStore` are thread-safe and hand out immutable snapshots. `MatchSetupService::Request`, `Reject` and `Cancel` run on the bridge, bench or Workbench thread; the names are resolved there (`Resolve` reads the files), so the game thread never touches the disk. `BeginStart` and `ApplyToStart` run on the MCC thread of the start, `UpdateLoad` on the game thread inside the first tick (`PlayerActionDetour`) and `UpdateBreak` on the game thread before the ticks of every frame (`SimulationTicksDetour`); none of them throws, and an exception after a request was taken ends it as Rejected for its number, with preset and map variant restored. The result of an old request never replaces the one of a newer request.

## Errors
A signature not found or a hook that fails to install logs an ERROR with the reason; nothing fails silently. A setup that cannot be applied is Rejected with its reason (a WARNING; ERROR when a write did not read back equal) and nothing of it is written: at the start the copy of the configuration is restored whole, at a round break nothing is written until every field passed its check. A roster that fails halfway has no rollback: the result is Applied (AtLoad) with the reason "partial: roster k of n operations done". A roster that fits the player table but not the match is only known at the first tick: after the preset and the map variant are in the start the result is AtLoad with a partial reason, never Rejected. A corrupted lifecycle
hook marks the engine destroyed and the main thread installs it again.

## Requirements
No other project reads memory, installs detours or touches the TLS except through this one.
